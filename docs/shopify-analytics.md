# Shopify analytics data flow

Shopify is the source of truth for subscription billing analytics. Rapi
Management stores only immutable Partner API facts and synchronization cursors:

- subscription charge lifecycle events;
- subscription sale transactions used for cadence and collected revenue;
- account lifecycle events used for customers, installs, growth, and retention;
- per-app high-water marks and resumable backfill cursors.

Most KPIs — active subscriptions, customers, growth, trials, churn, retention,
ARPU, and LTV — are calculated live when a report is requested, straight from
the raw immutable facts above. **2026-08-12:** a narrow, additive subset of
derived numbers (MRR, ARR, subscription counts, revenue) may also be
persisted as a rebuildable cache in `PartnerDailyMrrSnapshot` — one row per
app per UTC day, written incrementally by the same sync that writes the raw
facts (`app/lib/shopify/partner-mrr-snapshot.server.ts`). This does not make
the snapshot table a new source of truth: every field in it can be
regenerated byte-for-byte from the raw facts above, and it deliberately
excludes anything that either doesn't sum correctly across apps (distinct
active-customer counts — the same shop can use more than one app) or isn't
self-contained for a single day (30-day rolling churn). The read path falls
back to live reconstruction for any app/day range not yet snapshotted, gated
behind the `SNAPSHOT_READ_PATH_ENABLED` env var.

## Scheduled synchronization

Synchronization is a **pm2 cron process**: `rapi-management-sync` in
`ecosystem.config.cjs`, `cron_restart` every 5 minutes, running
`npm run sync:shopify`. It starts with `pm2 startOrReload`, so there is
nothing to configure by hand.

The lanes, in the order one run drives them
(`app/lib/shopify/sync-lanes.server.ts`, `LANE_NAMES` — the single source of
truth for what is scheduled):

| Lane                                      | Settles                 |
| ----------------------------------------- | ----------------------- |
| `POST /api/flex/cron/subscription-events` | resumes in chunks (202) |
| `POST /api/flex/cron/customer-events`     | resumes in chunks (202) |
| `POST /api/flex/cron/traffic-events`      | one bounded window/tick |
| `POST /api/flex/cron/app-reviews`         | resumes in chunks (202) |

Each lane answers 200 (nothing left to do), 202 (progress made, more
remains), or 503 (cannot progress); anything else is treated as retryable, so
an unexpected status can never make a run declare the backfill finished.

All require `X-Cron-Secret`, which lives in the server's `.env` and is read by
the script through the app's own env loader, so no part of this exposes the
application publicly to run the job. The requests go over
loopback to the live server process deliberately, so that process's own caches
are invalidated by its own writes and the fenced cursor leases stay owned by
the process holding them.

A run does deliberately bounded work (4-minute deadline, 12 iterations) and
exits 0 even with lanes still incomplete — an unconverged backfill is the
normal steady state, not a failure. Synchronization is sequential per app,
idempotent, and overlap-safe. Shopify Partner calls are kept out of page
loaders, so customer, subscription, overview, and report navigation reads the
local raw-fact mirror immediately.

To converge a large backfill without waiting for the 5-minute ticks, run
`npm run backfill:drain` on the host — same lanes, same cursors, much larger
budget.

Both subscription and account-lifecycle imports persist a Shopify cursor after
each successful page. Large histories therefore converge over multiple runs; an
interrupted run resumes from its last page instead of restarting the app's
history. Each lane call is bounded to eight minutes, and a lane that fails or
times out does not abandon the others — the next tick resumes every one of them
from the same cursors. A deploy's `pm2 startOrReload` may land mid-run for the
same reason it is safe to: fenced database leases plus persisted cursors mean a
killed run loses no progress.

Signed-in dashboard refreshes also start read-only, recent-window billing and
account-lifecycle syncs in the background. The route renders immediately from
immutable facts, then revalidates after Shopify responds. While the dashboard
stays open it verifies the newest windows every five minutes and again when a
stale browser tab becomes visible. A bounded request that needs more pages
returns `202` and resumes the same fixed min/max window on the next round; it
never replays page one forever. Database leases fence cron, browser, and
multi-worker refreshes for the same app and prevent older workers from
regressing a newer high-water mark.

Account-lifecycle derivation is also leased and bounded. Interactive refreshes
apply the newest relationship facts first, while the scheduler drains older
history. An older derivation backlog is reported separately and never causes
the browser to repeat already-complete Shopify billing requests. OAuth install
registration and uninstall webhooks advance the same relationship watermark,
so delayed Partner backfill cannot overwrite a newer live install state.

The UI treats three states separately:

- **Current exact billing data**: the recent billing window and full historical
  event and sale backfills are complete.
- **Latest window synced**: recent changes are present, while older history is
  still converging; sampled/partial KPIs are not labelled exact.
- **Synced through … / catching up**: at least one app or stream has not yet
  crossed the requested refresh watermark.

## Accuracy behavior

- Test charges are excluded.
- Annual subscriptions are normalized to monthly value for MRR and multiplied
  by 12 for ARR.
- Revenue is a period flow from successful subscription sale facts.
- Cancel-plus-replacement activation within 60 seconds is treated as a plan
  change, not churn.
- Trials are inferred from the initial activation billing date and first sale or
  cancellation evidence.
- LTV uses paid ARPU divided by rolling paid subscription churn and returns no
  value when churn is zero.

Partner transaction data is intended for analytics, not accounting. Credits,
taxes, refunds, payout timing, and Shopify revenue share require separate
authoritative reconciliation before they can be labelled as net payout.

## Operational checks

The overview marks an app `Live` only after both billing backfills have
completed and both recent billing streams are within the five-minute freshness
window. An app stays `Syncing` until the background or scheduled sync has
converged. If the dashboard is stale, verify:

1. `pm2 status` shows `rapi-management-sync` — a cron job, so `stopped` between
   ticks is healthy; what matters is a recent restart time.
2. `pm2 logs rapi-management-sync` (or `logs/sync-out.log`) shows a
   `sync run finished` line per tick, with per-lane states. `logs/sync-err.log`
   collects lane failures.
3. `CRON_SECRET` exists in the server's `.env`, and `PORT` in the sync
   process env matches the port the web process listens on — the script posts
   over loopback.
4. The app has a verified Shopify Partner connection and Partner App ID.
5. `npm run backfill:drain` to force convergence now; bounded cursors resume
   rather than restart, so this is safe to interrupt.
